# Caddy reverse proxy — NAS named-service reference

> **Why this lives in the vpn-speed-tester repo:** it doesn't belong *to* this project.
> It's cross-cutting NAS infrastructure that this project happens to depend on (the
> speed-test report is one of the proxied services). The authoritative config lives in
> the separate **`waitress`** repo (`/Users/impulse/repos/waitress`) and on the NAS.
> This folder is a **reference snapshot + runbook** so an agent working here understands
> what's running and how to add to it without re-discovering it every time.

## What Caddy does here

A single Caddy container (`slothcroissant/caddy-cloudflaredns`) runs in the
**`media-server-v4`** Portainer stack (stack ID **11**) on the NAS. It terminates HTTPS
for every `*.waitress.nickdeckerdevs.com` subdomain using **one wildcard Let's Encrypt
cert** (`CN=*.waitress.nickdeckerdevs.com`, issued by Let's Encrypt E8), obtained via the
**DNS-01 challenge** through the Cloudflare API. It then reverse-proxies each named host
to a backend container.

- **Config (routes):** `/volume1/Docker/caddy/Caddyfile` on the NAS — a **bind-mounted
  file**, *not* part of the compose body. Mirror in repo: `waitress/stacks/Caddyfile`.
- **Compose service:** `caddy:` block in `/volume1/Docker/PortainerCE/data/compose/11/docker-compose.yml`.
  Mirror in repo: `waitress/stacks/media-stack.yml`.
- **Certs/state:** `/volume1/Docker/caddy/data/` on the NAS.

## Exposure model (LAN-only — not on the internet)

1. Cloudflare DNS resolves `*.waitress.nickdeckerdevs.com` → **`10.1.10.254`** (the NAS's
   **private** IP), DNS-only / gray-cloud. Public DNS, but the address is unreachable
   from outside the LAN.
2. Let's Encrypt verifies ownership via **DNS-01** (a TXT record) — it never connects to
   the NAS. No HTTP-01, no ports 80/443 open to the world.
3. Caddy listens on the NAS only. **No router port-forwards, no Cloudflare Tunnel.**

Because the cert is a **wildcard**, **no per-service DNS record is ever needed** — every
`<anything>.waitress.nickdeckerdevs.com` already resolves. Naming a new service is purely
a Caddyfile route edit (see `add-a-service-runbook.md`).

## Where the secrets live

Caddy needs three env vars (`CLOUDFLARE_API_TOKEN`, `BASE_DOMAIN`, `ACME_EMAIL`). In the
compose file they are `${...}` interpolations, so they must be supplied at deploy time.

| Location | Role | Notes |
|----------|------|-------|
| **Portainer → stack `media-server-v4` → Environment variables** | **Source of truth at deploy time.** | Stored in Portainer's DB. A Portainer "update/redeploy" regenerates `stack.env` from here. **These must be set or Caddy crash-loops** (see history below). |
| `/Users/impulse/repos/waitress/.env` (local laptop, **gitignored**) | Local home for the same values | So you have them for local work/testing. Holds `CLOUDFLARE_API_TOKEN`, `BASE_DOMAIN=nickdeckerdevs.com`, `ACME_EMAIL=nickdeckerdevs@gmail.com`, etc. **Never commit.** |
| `/volume1/Docker/PortainerCE/data/compose/11/stack.env` (NAS) | What compose actually reads at `up` time | Regenerated by Portainer. Do **not** hand-edit as the durable fix — a future Portainer redeploy overwrites it. |

`ACME_EMAIL` is only the contact address Let's Encrypt uses for renewal-failure / policy
notices — never public. It is **`nickdeckerdevs@gmail.com`** (personal homelab address).

## History — the 2026-06-06 crash-loop (resolved)

Caddy was stuck `Restarting` with:
`parsing caddyfile tokens for 'email': wrong argument count … at /etc/caddy/Caddyfile:2`.
Root cause: `ACME_EMAIL` / `BASE_DOMAIN` / `CLOUDFLARE_API_TOKEN` were **absent from
Portainer's stored env**, so all three `${...}` interpolations resolved empty —
`email {$ACME_EMAIL}` collapsed to a bare `email`. The setup "worked on first publish,
broke on restart" precisely because the values existed only transiently and were never
persisted in Portainer.

**Fix (done):** the three vars were added to **Portainer's stored env** and the stack
redeployed. Caddy now serves all routes with a valid wildcard cert. This is the **durable**
fix — it survives future redeploys, unlike editing `stack.env` directly.
